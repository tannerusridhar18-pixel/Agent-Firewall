# IntentGuard / AgentFirewall V0.4 Prototype Dashboard

## 1. Purpose
The V0.4 Prototype Dashboard provides a graphical operator interface to manually exercise, observe, and verify the deterministic runtime security enforcement boundary of IntentGuard before connecting real autonomous AI agents and downstream MCP tool servers.

It visualizes the authoritative **8-gate security pipeline**, demonstrates real-time authorization states (`ALLOW`, `DENY`, `REQUIRE_APPROVAL`), exposes control-plane operations (task and session lifecycle, capability issuance, rotation, revocation, quarantine), allows execution of concrete security scenarios (Scenarios A through I), and features a dedicated **"Connect AI Agent"** control card with live connection testing and dynamic configuration export.

---

## 2. Architecture & Request Observability Flow

The prototype operates across a dual-tier architecture:
- **Frontend**: Next.js 16 (App Router, Tailwind CSS, TypeScript). Serves the dashboard UI on `http://localhost:3000` and transparently proxies control-plane (`/api/backend/*` → `http://127.0.0.1:8080/api/v1/*`) and MCP protocol (`/mcp` → `http://127.0.0.1:8080/mcp`) requests with zero CORS friction.
- **Backend**: Spring Boot 3.5.x + Java 21 + MySQL 8.4 + Flyway V4 (`agentfirewall` schema). Exposes the MCP gateway on `/mcp` and operator control-plane endpoints on `/api/v1/*`.

### The 8-Gate Gateway Pipeline
Every protected tool request sent to `/mcp` traverses 8 sequential enforcement gates:

```
[Agent / MCP Client]
        ↓
[POST /mcp (JSON-RPC 2.0)]
        ↓
Gate 1: Session & Quarantine Check   ──→ [BLOCKED if Session Quarantined or Inactive]
        ↓
Gate 2: Capability Validation         ──→ [FAIL-CLOSED: Token validated before tool manifest lookup]
        ↓
Gate 3: Tool Manifest & Arguments     ──→ [BLOCKED if Tool Unregistered or Invalid Target]
        ↓
Gate 4: Provenance Resolution         ──→ [FAIL-CLOSED: Unknown provenance rejected; sensitivity ranked]
        ↓
Gate 5: Categorical Risk & Policy     ──→ [Evaluates LOW / MEDIUM / HIGH / CRITICAL]
        ↓
Gate 6: Approval Resolution           ──→ [PAUSED: Awaiting approval on HIGH/CRITICAL; Atomic single-use consume]
        ↓
Gate 7: Fail-Closed Audit Evidence    ──→ [SYNCHRONOUS: DB failure halts execution; Request ID bound]
        ↓
Gate 8: Protected Tool Execution      ──→ [Downstream Tool / Adapter Execution]
```

## 3. How to Start Backend and Frontend

### Prerequisites
- Java 21+ & Maven 3.9+
- Node.js 20+ & npm 10+
- MySQL 8.x running locally on port 3306

### Environment Configuration
1. **Backend Database**:
   - URL: `jdbc:mysql://localhost:3306/agentfirewall?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=UTC`
   - User / Password: `agentfirewall` / `agentfirewall`
   - Flyway applies migrations `V1` through `V4`.
2. **Operator Credentials**:
   - `INTENTGUARD_CONTROL_PLANE_API_KEY`: `intentguard-control-plane-secret-key` (default)
   - Operator ID: `operator-admin` (default)

### Starting the Backend
```bash
cd backend
mvn spring-boot:run
```
Backend listens on `http://localhost:8080`. Verify with:
```bash
curl http://localhost:8080/api/v1/health
```

### Starting the Frontend
```bash
cd frontend
npm run dev
```
Frontend listens on `http://localhost:3000`.

## 4. Connecting a Real AI Agent / MCP Client

The dashboard includes a dedicated **"Connect AI Agent"** module that exposes real runtime connection parameters and lets operators test or export configurations for external MCP clients.

### Connection Parameters
- **MCP Endpoint**: `/mcp` (Direct: `http://localhost:8080/mcp`, Proxy: `http://localhost:3000/mcp`)
- **Protocol Version**: `2026-07-28`
- **Transport**: JSON-RPC 2.0 over HTTP `POST`
- **Session Identification**: `Mcp-Session-Id` header (matches an active record in `agent_sessions`)
- **Authorization Delegation**: `X-IntentGuard-Capability` header (matches a valid cryptographic token issued in `capabilities`)

### Connection Steps
1. **Provision Authorized Context**:
   - Click **"Provision Fresh Session & Capability"** (or **"New Demo Context"**).
   - This creates an authorized `Task` with defined tool scope, registers an `AgentSession`, and mints an active `Capability` token with a designated TTL.
2. **Export Configuration**:
   - The configuration cards dynamically reflect the active `Mcp-Session-Id` and `X-IntentGuard-Capability` token.
   - Select your client format and click **"Copy Config"**.
3. **Verify Gateway Handshake**:
   - Click the **"Test Connection"** button in the dashboard.
   - It performs real HTTP calls directly against `/mcp`:
     - `initialize`: Verifies MCP capability negotiation (`intentguard-mcp-gateway` v0.3.0).
     - `ping`: Confirms protocol liveness and JSON-RPC message framing.
     - `tools/list`: Queries enabled protected tools (`read_file`, etc.).

### Client Configuration Formats

#### A. Claude Desktop / Cursor (`claude_desktop_config.json`)
```json
{
  "mcpServers": {
    "intentguard": {
      "url": "http://localhost:8080/mcp",
      "headers": {
        "Mcp-Session-Id": "<CURRENT_SESSION_ID>",
        "X-IntentGuard-Capability": "<CURRENT_CAPABILITY_TOKEN>"
      }
    }
  }
}
```

#### B. cURL Command Line
```bash
curl -X POST http://localhost:8080/mcp \
  -H "Content-Type: application/json" \
  -H "Mcp-Session-Id: <CURRENT_SESSION_ID>" \
  -H "X-IntentGuard-Capability: <CURRENT_CAPABILITY_TOKEN>" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"read_file","arguments":{"target":"workspace/src/App.java"}}}'
```

#### C. Python Client Script
```python
import requests

url = "http://localhost:8080/mcp"
headers = {
    "Content-Type": "application/json",
    "Mcp-Session-Id": "<CURRENT_SESSION_ID>",
    "X-IntentGuard-Capability": "<CURRENT_CAPABILITY_TOKEN>",
}
payload = {
    "jsonrpc": "2.0",
    "id": 1,
    "method": "tools/call",
    "params": {
        "name": "read_file",
        "arguments": {"target": "workspace/src/App.java"}
    }
}
response = requests.post(url, json=payload, headers=headers)
print("Decision / Content:", response.json())
```

## 5. Agent → IntentGuard → Protected Tool Flow

When an AI agent executes actions through IntentGuard:

```
+----------------+                +-------------------------+                +------------------------+
|    AI Agent    |                |  IntentGuard Gateway    |                | Downstream Tool Server |
|  (MCP Client)  |                |       (Port 8080)       |                |     (Local/Target)     |
+----------------+                +-------------------------+                +------------------------+
        |                                      |                                          |
        | 1. POST /mcp (initialize)            |                                          |
        |------------------------------------->|                                          |
        |    JSON-RPC 2.0 handshake            |                                          |
        |<-------------------------------------|                                          |
        |                                      |                                          |
        | 2. POST /mcp (tools/list)            |                                          |
        |------------------------------------->|                                          |
        |    Discovers authorized tools        |                                          |
        |<-------------------------------------|                                          |
        |                                      |                                          |
        | 3. POST /mcp (tools/call)            |                                          |
        |    Headers: Mcp-Session-Id,          |                                          |
        |             X-IntentGuard-Capability |                                          |
        |------------------------------------->|                                          |
        |                                      | Gate 1: Check Session & Quarantine       |
        |                                      | Gate 2: Validate Capability Token        |
        |                                      | Gate 3: Match Tool Manifest & Arguments  |
        |                                      | Gate 4: Resolve Provenance & Sensitivity |
        |                                      | Gate 5: Evaluate Categorical Risk Policy |
        |                                      |                                          |
        |                                      | [If Policy requires Operator Approval]: |
        |                                      | Gate 6: AWAITING_APPROVAL                |
        |<-------------------------------------|                                          |
        |    Status: REQUIRE_APPROVAL          |                                          |
        |    Error: Request ID returned        |                                          |
        |                                      |                                          |
        |                                      | [Operator approves in UI]                |
        |                                      |                                          |
        | 4. Retry tools/call                  |                                          |
        |    Header: X-IntentGuard-Approval    |                                          |
        |------------------------------------->|                                          |
        |                                      | Gate 6: Consume Approval (Single-Use)    |
        |                                      | Gate 7: Persist Synchronous Audit Record |
        |                                      | Gate 8: Dispatch Execution ------------->|
        |                                      |                                          | 5. Execute Tool
        |                                      |<-----------------------------------------|
        |<-------------------------------------|
        |    Return Tool Result / Output       |
        |                                      |
```

## 6. Local Database Reset & Test Data Cleanup

To start from a completely clean state without modifying Flyway migration scripts or deleting registered tool manifests, execute the following SQL in MySQL:

```sql
USE agentfirewall;

SET FOREIGN_KEY_CHECKS = 0;

-- Wipe transient execution & audit data
TRUNCATE TABLE session_quarantines;
TRUNCATE TABLE approvals;
TRUNCATE TABLE capabilities;
TRUNCATE TABLE agent_sessions;
TRUNCATE TABLE tasks;
TRUNCATE TABLE security_events;
TRUNCATE TABLE security_decisions;
TRUNCATE TABLE activity_events;

SET FOREIGN_KEY_CHECKS = 1;
```

### Verified Empty States
Upon clearing runtime data:
- **Task & Session Card**: Displays `"No active session"`
- **Capability Card**: Displays `"No active capability"`
- **Connect AI Agent Card**: Shows `<NO_ACTIVE_SESSION>` / `<NO_ACTIVE_CAPABILITY_TOKEN>` in config previews, prompting the operator to provision fresh credentials.
- **Audit Table**: Displays `"No security events"`
- **Decision Inspector**: Displays `"No requests executed yet."`

No fake, mock, or hardcoded records are shown.

## 7. Available Security Demonstrations (Scenarios A through I)

The prototype provides one-click verification for all 9 core security invariants:

| Scenario | Trigger / Condition | Enforcement Point | Expected Result | Reason Code |
| :--- | :--- | :--- | :--- | :--- |
| **A. Valid Request** | Valid token, active session, task scope `workspace/*` | Gate 8 Reached | **ALLOW** | `ALLOW` (Content returned) |
| **B. Missing/Invalid Token** | Missing or forged `X-IntentGuard-Capability` | Gate 2 | **DENY** | `MISSING_CAPABILITY` / `INVALID_TOKEN` |
| **C. Invalid Provenance** | Non-existent ref `prov-nonexistent-ref-001` | Gate 4 | **DENY** | `INVALID_PROVENANCE_REF` |
| **D. High-Risk Action** | Elevated session denials (>= 2 denials) | Gate 5 → Gate 6 | **REQUIRE_APPROVAL** | `AWAITING_APPROVAL` (Generates Request ID) |
| **E. Operator Approved** | Operator approves pending request, retries with header | Gate 6 → Gate 8 | **ALLOW / EXECUTE** | `ALLOW` (Single-use consumed) |
| **F. Approval Replay** | Retries MCP request with already-consumed approval | Gate 6 | **DENY** | `APPROVAL_ALREADY_CONSUMED` |
| **G. Quarantined Session** | Requests on quarantined session | Gate 1 | **DENY** | `SESSION_QUARANTINED` (Pre-capability check) |
| **H. Revoked Capability** | Request using revoked capability token | Gate 2 | **DENY** | `CAPABILITY_REVOKED` |
| **I. Expired Capability** | Request using capability token past expiration TTL | Gate 2 | **DENY** | `CAPABILITY_EXPIRED` |

## 8. Known Limitations

1. **In-Memory Token Cache in Prototype**:
   - The dashboard keeps the raw capability token in local client state for demonstration purposes only. Tokens are masked (`••••••••`) in the display. In production V0.6+, tokens are held exclusively by the agent client or credential vault.
2. **Downstream Tool Implementations**:
   - V0.4 provides the protected mock tool `read_file`. Real file system or shell execution tools remain gated by adapter manifests in subsequent versions.
3. **No Attack-Lab Harness in V0.4**:
   - Automated adversarial injection suites and red-teaming harnesses are scheduled for V0.5.
