# V0.3 Capability-Based Authorization & MCP Gateway Integration

V0.3 implements cryptographic, task-scoped capability authorization enforced fail-closed at the MCP Gateway.

## Architecture & Security Invariant

Flow:
```
AI Agent / MCP Client (with Mcp-Session-Id & X-IntentGuard-Capability)
  → IntentGuard MCP Gateway (/mcp)
      [Gate 1: Session Status Check]
      [Gate 2: Capability Validation BEFORE tool lookup]
      [Gate 3: Tool Manifest Lookup]
      [Gate 4: Deterministic Policy Engine Evaluation]
  → Protected Tool Execution
  → Target Resource
```

**Security Invariant:** Missing, invalid, expired, revoked, or out-of-scope capabilities are denied immediately with zero downstream tool lookup and zero execution.

## MCP Protocol Endpoint

- **URL:** `POST http://localhost:8080/mcp`
- **Supported Methods:**
  - `initialize`: Returns gateway server info (`intentguard-mcp-gateway` v0.3.0) and supported capabilities.
  - `ping`: Standard health ping returning `{}`.
  - `tools/list`: Returns all enabled tool manifests from `mcp_tool_manifests`.
  - `tools/call`: Executes a protected tool subject to capability and policy validation.

## Capability Model & Validation Rules

A capability contains:
- `capability_id`: Unique identifier (e.g., `CAP-<uuid>`)
- `task_id`: Bound to a specific task
- `tool_name`: Bound to a specific tool (e.g., `read_file`)
- `resource_scope`: Target resource scope (exact match or wildcard prefix such as `workspace/src/*`)
- `token_hash`: SHA-256 hash of the unforgeable raw token
- `status`: `ACTIVE` or `REVOKED`
- `issued_at`: Timestamp of issuance
- `expires_at`: Timestamp of expiry (maximum TTL: 24h)
- `revoked_at`: Timestamp of revocation

### Enforcement Matrix

| Condition | Gateway Result | Downstream Tool Executed? |
|---|---|---|
| Valid token, matching task/tool/scope, active, unexpired | `ALLOW` → passes to policy engine | Yes (if policy allows) |
| Missing token header | `DENY` (`CAPABILITY_REQUIRED`) | No |
| Unknown / tampered token | `DENY` (`INVALID_CAPABILITY`) | No |
| Task mismatch | `DENY` (`CAPABILITY_TASK_MISMATCH`) | No |
| Tool mismatch | `DENY` (`CAPABILITY_TOOL_MISMATCH`) | No |
| Revoked token | `DENY` (`CAPABILITY_REVOKED`) | No |
| Expired token | `DENY` (`CAPABILITY_EXPIRED`) | No |
| Target outside resource scope | `DENY` (`CAPABILITY_SCOPE_DENIED`) | No |

## Control-Plane Requirement: Capability Issuance

To prevent security vulnerabilities, IntentGuard deliberately does **not** expose an unauthenticated capability-issuance REST endpoint. Capabilities are created internally via `CapabilityService.issue(...)`.

The next control-plane milestone will introduce an authenticated and authorized control-plane API and/or operator dashboard for secure credential and capability issuance and lifecycle management.
